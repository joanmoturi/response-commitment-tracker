## Existing documented application flow

The root README describes a browser frontend using a same-origin API proxy to
the FastAPI backend, database-backed authentication, and bounded agent execution.
PostgreSQL/pgvector is the documented deployment database; local SQLite has
explicit development-only limitations. This document does not verify those
behaviors by execution or code audit.

Keep the root `README.md` and `backend/README.md` as the detailed application
references rather than duplicating their configuration and API documentation.
They identify outstanding production gates, including limits of inline agent
execution and the need for deployment-specific controls.

## Response-tracker pilot MVP (October 16, 2026)

The existing FastAPI / Next.js stack was retained. No dependencies or external
services were added.

### Request data flow

The browser uses the existing same-origin API client and in-memory bearer
session. FastAPI validates the request and resolves the authenticated `User`.
The `/api/v1/requests` router scopes every read and mutation by that user's ID.
SQLAlchemy persists request details in `tracked_requests`; migration `0002`
adds the table, consistency constraints, and a composite account/status/deadline
index. The local SQLite launcher uses `Base.metadata.create_all`; production
databases use Alembic `upgrade head`.

Each record stores a title, details, owner name/contact, UTC deadline, open or
completed status, optional response, and timestamps. Database checks constrain
status and completion timestamps. The API reports overdue as a derived value:
the request must be open and its deadline must be strictly earlier than current
UTC time. No stale overdue flag is persisted.

### Key decision

The first pilot is private per application account, with a free-form owner
name/contact. Alternatives included introducing team and membership entities
plus invitations and assigned-user authorization. That was deferred because the
product has no customer evidence and the existing auth model has no team
boundary. This reduces implementation and authorization risk but does not
provide shared team visibility; see `product-spec.md`.

### Operational trade-offs

- There is no delete operation, avoiding accidental destructive loss in the MVP.
- Open requests can be edited; completion is a one-way transition with an
  optional response. Invalid transitions return conflict errors.
- Request creation accepts a client-generated UUID submission key unique within
  the account. The browser reuses it for retries and clears it when the form is
  edited; the database constraint makes repeated submissions idempotent.
- Search is parameterized and treats SQL wildcard characters literally.
- API pagination is bounded to at most 100 records per page. There is no request
  retention, export, or backup-specific recovery workflow yet.
- PostgreSQL migration SQL is generated by the test suite, but no PostgreSQL
  database was migrated during this task.
